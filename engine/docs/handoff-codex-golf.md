## Why

A VR golf game: the player swings a club with a hand, the ball rolls on a course (hills, greens, sand, water) and drops into cups. `ve-game` has a flat `ground y=` plane and no rolling or striking. Research notes behind the numbers: a small ball and a thin fast club head tunnel through each other between steps unless the head is swept (so test the head's *segment*); on a green a ball slows at a roughly constant rate (stimp 10 is about 0.55 m/s^2) and a slope adds a pull; a cup takes a ball moving slower than about 1.6 m/s (our choice, no source).

## What to build

The header of `crates/ve-game/tests/golf.rs` is the contract (read it first, line by line). In short:

1. `pub struct GroundField` (exported from the crate root) with `new(origin: [f64; 2], cell: f64, nx: usize, nz: usize, heights: Vec<f32>, surfaces: Vec<u8>) -> Result<Self, String>` (refuse: sizes that do not fill the grid, a cell that is not finite and positive, `nx` or `nz` under 2, a non-finite origin), `height(x, z) -> Option<f64>` (bilinear; `None` outside or when any of the four samples is NaN), `normal(x, z) -> [f64; 3]` (from the height gradient; `[0, 1, 0]` where there is none), `surface(x, z) -> u8`. `World::set_ground(&mut self, Option<Arc<GroundField>>)` and `World::ground()`; the field is **not** part of the snapshot or hash (like the navmesh).
2. Text: kind keys `roll=1`, `strike=1`, `reach=M` (default 0, >= 0), `loft=DEG` (default 0, 0 to 80), `power=F` (default 1, > 0, at most 5), `cup=1` (each 0/1 as `fall` is; anything else is a diagnostic naming the key); `surface NAME parts=a,b decel=D bounce=B` (decel > 0, bounce 0 to 1; ids 1, 2, ... in order; the default surface 0 has decel 1.0, bounce 1.0); `terrain parts=a,b cell=M` (parts required, cell > 0, default 0.25). `GameDef::surfaces() -> &[SurfaceDef]` (pub fields `name, parts, decel, bounce`) and `GameDef::terrain() -> Option<&TerrainDef>` (pub `parts`, `cell`); all of it in `describe()` and round-tripping, with diagnostics (line, column, message naming the key, suggestion) like the other lines.
3. Rolling (`src/world/state/rolling.rs`): the exact rules in the test header. Order inside a step: hands (grab/carry/release) -> club strikes -> rolling/air integration -> cups -> `touch` events. A `roll` thing that is held by a hand is carried like any grabbed thing (it is also `grab=1` if the kind says so) and does not roll.
4. Clubs (`src/world/state/club.rs`): `Inputs::hand_rotations: Vec<HandRotation>` (new pub struct `HandRotation { pub side: HandSide, pub rotation: [f64; 4] }` exported; `Inputs` keeps `Default` so `..Inputs::default()` literals elsewhere still compile); per-step head position and its three-step history per club in world state (included in snapshot/restore); the swept test, the speed rule, the latch, `strike` events: exactly as the header says. `Entity::orientation: [f64; 4]` (default `[0, 0, 0, 1]`), set from the hand's rotation each step for hand-followed things (identity when the hand has no rotation or is untracked).
5. Cups: `sink` events as the header says.
6. Determinism: no hash-map order, no time. The new state (club histories, strike latches, anything the rolling needs between steps) is in the snapshot, and in the hash **only when some kind has `roll`, `strike` or `cup`** (so every other game keeps its exact hash: the last test checks it).
7. `ve-game` stays free of rendering and of any host types.

Owner needs to resolve the test/contract conflict; the implementation retains gravity.
