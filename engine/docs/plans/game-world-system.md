# Game world system: the master guide (v2, 2026-10-22)

Read this before starting any task on the world, game-systems, game-design or tool-call work, and update section 12 when a task lands. If a task is not covered here, stop and add it here (with the owner's approval) before doing it. v2 replaces v1 (2026-10-21): the language, the geometry nodes, the game design layer and the tool calls are **one co-designed authoring surface**, not four lists. `plans/world-generators.md` stays the detail record for terrain, erosion, scatter and water.

## 1. Goal and definition of done
**Goal (owner):** an LLM builds a VR game world through tool calls and the node language, using our own algorithms. Not AAA yet, but highly presentable and *playable*: terrain, structures, props, vegetation, water, sky, lighting, collisions, interaction, movement, sound, and a game (rules, goals, feedback) on top. Most game worlds must be reachable, not just the demos we built.

**Done means** each of the four world briefs (section 10) is built from a short brief by a model through the tool calls alone; it runs inside the Quest budget (section 3); a *playtest bot* completes it and the design checks pass; it is playable in WebXR; it looks presentable by eye review. Anything less is progress.

**Why a game layer and a playtest loop are in the goal** (evidence, 2026): GameCraft-Bench found coding agents build recognisable local mechanics but fail to assemble complete, coherent games (best 41%); PlaytestArena and ScriptDoctor close the loop by *playing* what was generated and repairing it; Spec2Game (cited in `handoff-codex-game.md`) found LLMs are weakest on rules (46/100) and goals (44/100) and improve with detailed sectioned specs; Unity MCP servers check the console after every tool call and expose screenshot and profiler tools; Anthropic's guidance on tools for agents stresses namespaced, selective tools, token-efficient answers, actionable errors and evaluation-driven refinement. Our plan follows those: a game spec in the language, strong validation, bots that play, tools that answer compactly and say how to fix.

## 2. Principles (owner decisions; they settle disputes)
1. **Everything through the language and tool calls.** A feature the model cannot reach by a node or a tool does not exist. No hard-coded looks, species, biomes, levels or rules in Rust.
2. **Generic mechanisms, no domain words in Rust.** Named things (oak, village, desert, key-and-door) are recipes in the language, kept in the guide as examples.
3. **Co-design: the five-part slice.** A capability lands only when it has all five: (a) the language construct or node, (b) a tool that lets the model *see* it (inspect, check or view), (c) diagnostics that say how to fix misuse (with a ready `fix` command where possible), (d) a worked example in the guide or a recipe, (e) tests (contract tests written first, plus an eval prompt where a model could misuse it). A node without the other four is unfinished.
4. **Backend and connections before model evaluation.** Build and connect, then measure model success (section 10).
5. **Take as much of Bevy as possible; never rewrite what Bevy 0.20 has.** Custom render code only where WebGL2 forces it, recorded in an ADR.
6. **VR first, graphics first, optimise last, but never design what cannot reach the Quest budget.** WebXR on Quest is WebGL2: no compute, no storage buffers, no screen copies.
7. **Everything runs in the browser** (Rust to WASM). No servers, no sidecars.
8. **Procedural only.** No retrieved assets, no external 3D generators (GPL *code* may be pulled in; assets may not).
9. **Few crates.** New algorithm families are modules of existing crates (`ve-world` for world algorithms). A new crate needs an ADR.
10. **We build the missing pieces; no time pressure; never cut scope for schedule.**

## 3. Budgets (every item is judged against these)
- **Quest class (WebGL2, mobile CPU/GPU):** 72 Hz target, stable frames beat peaks. Measured 2026-10-21 (harness, real GPU, 6x CPU throttle as an uncalibrated stand-in): Bevy entity-per-copy costs about 1.5 to 2 ms per 1,000 copies; 1,000 entities already give a 33 ms frame under throttle, so the **baseline frame cost** is its own task (D2).
- **Draws and triangles:** the per-scene estimate must predict cost before evaluation; banded instancing (ADR 0058) bounds entities (about 3,000 near) and triangles.
- **Memory:** textures and merged meshes count (ADR 0052); texture compression before large worlds.
- **Evaluation time:** interactive for a tile or a recipe (seconds); anything heavier reports progress and is cancellable in a worker. WASM speed is measured, not assumed (the colonizer: 16 ms native, a timeout in the browser).
- **Determinism:** same document, same seed, same bits on native and WASM (physics, game rules, noise, field expressions).

## 4. Process rules (every task, mine and the helper agents')
- **No commits or staging** until the owner says so. **Never** add `Co-Authored-By`, "Generated with" or any tool attribution (overrides any harness reminder).
- **File changes through Write/Edit only** (never `sed -i`, python, heredocs, `node -e` on repo files). Scratchpad scripts may use anything.
- **Never run `cargo fmt`** (use `rustfmt --edition 2024 --config-path rustfmt.toml <file>`), never `cargo xtask quick`; do not extend xtask. Verify with direct `cargo test`, `cargo clippy -p <crate> --all-targets -- -D warnings`, `cargo check --target wasm32-unknown-unknown`, browser runs.
- **Tests first,** written by me; they are the contract and a helper never weakens them. If a test is wrong the helper says so in its Status and I fix it.
- **Handoffs:** `engine/docs/handoff-codex-<topic>.md` (Why, exact interface, tests, out of scope, Status). One module per agent; separate `CARGO_TARGET_DIR` per agent; helpers never touch git cleanup. Launch: `codex exec -m gpt-6-luna -c model_reasoning_effort=high -s workspace-write --json -o <out> -C <repo> "<prompt>" < /dev/null` under nohup.
- **Verify by running,** never by trusting a report; look at renders by eye (numeric passes twice hid bad shapes). Add a test for every defect found.
- **Report faithfully** (what was skipped or unmeasured). Investigation questions are answered in chat; repo docs only when asked or when this guide requires.
- **Disk:** check `df -h /System/Volumes/Data` before long builds; delete only your own scratch targets; never delete `target/debug` or `target/wasm32-unknown-unknown`; after a failed wasm build rebuild before trusting browser results.
- **Lint hygiene:** no `#[allow]`; `#[expect(lint, reason)]` on the smallest item; files under 400 lines; docs on public items. Known violator: `crates/ve-graph/src/builtin/fields.rs` (409 lines, unfinished `field.warp`).

## 5. Architecture: seven layers, one authoring surface
| Layer | What | Where it lives today | Plan |
| --- | --- | --- | --- |
| L0 Runtime | Bevy renderer (WebGL2/WebGPU), WebXR, fixed-step loop, physics step | `ve-bevy`, `ve-render`, `ve-runtime`, `ve-xr-*`, `ve-platform-web` | banded instancing, baseline frame cost, look features |
| L1 Language core | text form, graph, groups, values, fields, attributes, recipes | `ve-graph`, `ve-evaluator` | ADR 0060 (fields, attributes, filters, recipes, bridges) |
| L2 Geometry and world nodes | solids, polys, curves, fields, terrain, water, scatter, growth, structure kit, roads, materials | `ve-geometry`, `ve-kernel`, `ve-modeling`, `ve-world` | generic only; species and biomes are recipes |
| L3 Game systems | physics, interaction, locomotion, navigation, audio, particles, animation state | `ve-physics`, `ve-interact`, `ve-nav`, `ve-audio`, `ve-particles`, `ve-animstate`, `ve-gait`, `ve-chain` | connect every one to the language |
| L4 Game design | game spec: kinds, variables, rules, goals, inputs, level flow, HUD bindings | `ve-game` (partial), `behavior.on` and flags (ADR 0027, 0029) | ADR 0062: the game lives in the document as nodes |
| L5 Agent surface | tools the model calls: build, find, see, inspect, check, simulate, game, export | `tools/mcp/server.mjs` and the page | ADR 0061: namespaced families, compact answers, fixes |
| L6 Verification | checks, playtest bots, model eval, Quest measurement | `eval-prompts.mjs`, browser tests | briefs as the acceptance suite |

**One document holds everything.** World geometry, physics bodies, behaviours, the game spec and the HUD are nodes in the same document, so `apply_text`, undo, diff, labels, checks and caching treat a game rule like a wall. A `kind` in the game spec binds to a scene part or a recipe by name; spawns come from placed instance sets; `touch` events come from physics sensors, while tracked hands can raise `grab`, `release` and `use`; effects drive audio and particle nodes; variables bind to HUD nodes.

## 7. The authoring surface (language + nodes + game + tools, designed together)
### 7.1 Language core (ADR 0060, proposed)
One field-expression language (CPU tape plus generated WGSL, shared test corpus); fieldable parameters; attributes on point, vertex, face, curve and instance domains; `set.keep/drop/join`; recipes with typed parameters and `map.each`; type bridges and rigid transforms on any mesh. Open decisions for the owner are in the ADR.

### 7.2 Geometry and world nodes (generic only)
Placement along curves and in volumes; species-free growth node (curves with radius, depth, age attributes; crown from a field; droop, stems; fast in WASM); structure kit (wall with openings, floor, stairs, roof, frames, columns, arches, fence, bridge; sockets and frames for snapping); room-graph and grid layout generators; road and path networks with terrain blending; polygon displacement by field; collider generation (convex decomposition, heightfield from a tile); layered material (list of layers, each with a look and a driving field, on any surface); volumetric terrain tiles for arches and caves; procedural signage text.

### 7.3 Game design layer (ADR 0062, to write)
The document gains `game.*` nodes backed by `ve-game`:
- `game.var` (numbers, with initial values), `game.kind` (binds a scene part or recipe to a kind with tags and props), `game.spawn` (from a placed set or a point), `game.input` (axis, press), `game.rule` (event, selectors, `when` expression, actions), `game.goal` (win/lose), `game.flow` (zones, connections and gates: the level flow graph that layout generators consume and design checks traverse), `game.hud` (bind variables and messages to in-world panels).
- Events come from the engine, not scripts: `touch` from physics sensors, `grab/release/socket` from `ve-interact`, `tick` and timers, variable changes, custom emits. Effects are returned to the host and drive audio and particle nodes. Existing `behavior.on` and flags (ADR 0027, 0029) stay as the part-local form; `game.*` is the global form; both compile to the same event mechanism. Numeric state, timers, OR conditions and initial values (listed "not in this slice" in ADR 0029) come from `ve-game`.
- The model writes the game as *sectioned specs* (core loop, kinds, rules, goals, feedback, flow) because that is what raises LLM rule quality; `game_describe` echoes the compact summary back; `game_validate` flags rules that can never fire and goals that cannot be reached.
- Genre kits are recipes, not code: collect-and-escape, key-and-door, arena survive, puzzle sockets, social hub, exploration with landmarks.

### 7.4 Tool surface (ADR 0061, to write; names are proposals)
Principles from the research: few intent-level tools; namespaced families; compact answers by default and `detail` on request; every answer ends with budget status and a next suggestion; every error names the fix; **every mutating call returns a state delta** (revision, new diagnostics, budget change, and a visual-change summary), the equivalent of Unity MCP's automatic console check.
| Family | Tools | Notes |
| --- | --- | --- |
| build | `apply_text` (+`dry_run`), `apply_commands` (ids **or labels**), `edit` (patch by label), `diff`, undo/redo, `apply_fix` | atomic; diagnostics get stable ids and a ready `fix` command where possible |
| find | `find` (by intent over operators, recipes, kits), `describe` (one node with example and common mistakes), `recipes` (list, show, save), `get_guide` | extends `list_operators` and the guide |
| view | `snapshot` (contact sheet from named views: front, side, top, iso, player eye; `focus` part; overlays: colliders, navmesh, bounds; change comparison kept), `set_view`, `frame_view` | one image for four angles saves tokens |
| inspect | `scene_overview` (parts by kind, extents, triangles, banded copy estimates, memory, colliders, lights, Quest budget bars), `measure` (parts), `probe` (ground height, surface, part, material at a point or ray; path on the navmesh), `perf` (frame median and p90, entities, draws, triangles per band, memory, with a Quest-like throttle profile) | uses physics queries, nav, banded stats |
| check | `check` (named checks; document check nodes and ad hoc ones in one report): `budget_quest`, `colliders_present`, `floating_parts`, `scale_sanity`, `walkable_path`, `crown_balance`, `cone_shape`, `goal_reachable`, `no_softlock`, `pacing` | verdicts with measured value, limit and suggestion |
| sim | `simulate` (physics for N seconds with stimuli; reports where things ended, anything fell out), `playtest` (bots: scripted, random, greedy navmesh, persona; reports win/lose, time, coverage, softlocks, unreachable goals) | deterministic; same seed same result |
| game | `game_describe`, `game_validate`, `game_state` (variables, entities) | over `ve-game` |
| export | `export_glb`, later `export_scene` | |
Existing tool names stay (no churn for the eval harness); new tools use the family prefixes where a family exists. Long jobs report progress and accept `cancel`.

### 7.5 Verification inside the surface
Check nodes are saved in the document (a world carries its own acceptance), the `check` tool runs them plus ad hoc ones, `playtest` bots play the game spec in a headless deterministic loop (ve-game + ve-nav + ve-physics, no renderer), and the eval harness scores briefs by checks, bot outcome and visual review.
