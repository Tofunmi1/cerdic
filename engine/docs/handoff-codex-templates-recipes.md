## What to build (JS in `tools/mcp/`; the page side only if a template must be applied)
1. **`start_from {template?: string, apply?: boolean}`**: no argument lists templates as JSON `{templates: [{name, about, nodes, kind}]}`. With a name it returns `{name, about, text, change: [...], notes}`: `text` is the whole working document (compact text form) and `change` is a list of at least two concrete suggestions of what to edit to make it a different thing (what a model would change first: counts, sizes, colours, names, rules). `apply: true` applies it to the editor document through the same path as `apply_text` and returns that answer (without a page: the usual "No editor page is connected" error). Unknown name: error listing the names.
   Templates (files in `tools/mcp/templates/<name>.txt` with a small header comment block read for `about`/`kind`/`change`; create them by reading the world files with your tools and writing the text with your write tool, NOT cp): `rolling-course` (from `web/dist-bevy-gpu/worlds/minigolf2.txt`: a hands-first game on real terrain with a rolled ball), `creature-game` (from `blackout2.txt`: patrolling creatures, throwing, lives), `chase-arena` (from `creature_chase.txt`), `district` (from `city_district.txt`: streets, blocks, towers). Keep each template's game or scene intact; the `change` hints must be true of that text.
2. **`recipes {action: list|save|show|delete, name?, text?, about?}`**: recipes are model-written groups saved on the server for reuse across sessions, stored one file per recipe in `VE_RECIPES_DIR` (default `tools/mcp/recipes-local/`, add it to `.gitignore` if the repo has one for tools) as `<name>.txt` with the `about` in a first comment line. `save` requires: name lowercase letters, digits, underscore, at most 32; `text` is exactly one `group NAME ... end` whose name equals `name`; the name must not collide with a built-in kit (`list_operators` kit names). `list` returns `{recipes: [{name, about, params}]}` where `params` are the `expose` names. `show` returns the source and a call line to paste (`name(width=<default>, ...)`; defaults from the exposed members' values when readable, else the names alone). `delete` removes it. Errors name the fix.
3. **Use in a document**: `show` returns the source and the model pastes it ahead of its program like a kit (the guide's reuse topic says how). Do not change `apply_text`.
4. **Stable order**: `tools/list` returns the same names in the same order on every call and across versions of the server (sort by a fixed order list in the manifest, new tools appended) so prompt caching keeps working; the test checks two calls agree.
5. **Guide**: topic `recipes` (add to the menu) explains `start_from` (start from a working skeleton and edit, this is the fastest way to a good result), `recipes` (save what you build twice) and gives three worked `run` examples: build a program then check and read the delta in one call; loop over a list of positions calling `apply_text` with a pipe line each; apply `edit` ops then `diff` and return only the changed lines.
6. Keep tool definitions short (each ≤ 1,100 characters for the two new tools; total under 13,000).
