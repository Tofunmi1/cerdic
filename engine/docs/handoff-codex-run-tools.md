# Handoff: measure runs, tips in tool answers, and an aiming playtest policy

Findings that drive this (2026-10-26, `gpt-6.1-sol`, one run each): a cottage took 15 calls with 7 spent orienting, and 8 calls once the guide/operators could be fetched together and the server introduced itself; a mini-golf rebuild took 153 calls (57 on look-around) and then 95 after the orientation fixes, but its game cannot be won and the model's own "test" was a teleport of the pocket rules, not strokes. We have no per-run token or time numbers saved, and nothing nudges a model toward `batch`, `get_guide` with `topics`, or `snapshot` with `cameras` when it does not find them itself.

Three independent pieces. Work on them in this order; they touch different files.

## A. Run metrics (`tools/mcp/run-metrics.mjs` + `tools/mcp/try-animated.mjs`)
Test (already written, do not weaken): `tools/run-metrics-test.mjs` (`bun tools/run-metrics-test.mjs` from `engine/`).
- `summarizeCodexEvents(text)`: reads the Codex `--json` event log (one JSON object per line; ignore lines that do not parse). Count `item.completed` items of type `mcp_tool_call` (one per call), by `tool`, failed ones (`error` not null) as `errors`, the characters of `result.content[].text`, the last `agent_message` text as `answer`, and `turn.completed.usage` (`input_tokens`, `cached_input_tokens`, `output_tokens`; `uncachedInputTokens` = input - cached). Also `looks` (snapshot, set_view, frame_view), `orientation` (get_guide, list_operators, get_text, get_nodes, find, scene_overview) and `builds` (apply_text, apply_commands, edit, batch, run). Return all numbers as shown in the test.
- `aggregate(runs)` and `formatTable(runs)` as in the test (min, median, mean, max for `toolCalls`, `uncachedInputTokens`, `outputTokens`, `seconds`).
- Wire it into `try-animated.mjs`: after the Codex agent branch, call `summarizeCodexEvents` on the events it already writes, measure wall seconds, and save `metrics` (the summary plus `seconds`) in the world's `.json`; print one line `metrics: calls N, uncached input X, output Y, Z s`. For the `claude` agent branch compute what you can from `calls` and seconds only. Add `--repeat N`: runs the whole request N times as `<name>_1` ... `<name>_N` on consecutive ports starting at `--port`, each from a fresh seed, then prints `formatTable` and the `aggregate` for the set. Add a small CLI `tools/compare-runs.mjs <name>...` that reads `web/dist-bevy-gpu/worlds/<name>.json` files and prints the table and aggregate.

## B. Tips in tool answers (`tools/mcp/hints.mjs` + `tools/mcp/server.mjs`)
Test (already written): `tools/hints-test.mjs`.
- `createHints()` returns `{note(tool, args, isError) -> string | null, reset()}` with the rules the test checks; each tip kind fires at most once per session, every tip starts `Tip:` and is at most 260 characters, and a tip names the exact call to make (for example `Tip: get_guide takes topics: ["curves","terrain"] and operators: {family: "solid"} in one call.`).
- In `server.mjs`, after a tool answer is built in `callTool`, append the tip as a final text line (`\n\nTip: ...`) to a plain-text answer. Never append to answers that are structured JSON the client parses (the `batch` and `run` answers, `get_text` JSON, `start_from`, `recipes`, `check` and similar: any answer whose text starts with `{` or `[`), and never to image answers; tips for those tools may be remembered and attached to the next plain-text answer instead. Calls inside a `batch`/`run` also count (call `note` from the shared dispatcher). `reset()` runs on server start.

## C. The aiming playtest policy (`web/aim-policy.js`, `playtest` page handler)
Test (already written): `web/tests/aim-policy.test.ts` (`cd web && bun test`).
- `web/aim-policy.js` (plain JS, ES module, no dependencies): `planShot`, `nextScale`, `swingFrames`, `parseAimPolicy` as the test specifies (the shot-size maths is the one in `tools/minigolf-verify.mjs`: integrate v^2 backwards along `ground.profile` samples, `v^2 += 2 * max(0.05, decel + 5/7 * 9.8 * slope) * ds`, floor 0.5, cap 16; `swingFrames` holds the hand still for 8 frames 0.6 m behind the ball, then moves it along the direction at the planned speed through the ball until 0.5 m past it, with the head 0.9 m out along -Z of the hand; it returns hand positions `[x, y, z]` per frame and does NOT include the retreat the verify script adds afterwards).
- The `playtest` tool's `policy` accepts `aim:<thing tag>:<target tag>[,<target tag>...]` (general names: any hand-held tool that strikes a rolling thing toward a target). Wire it in the page handler that runs `playtest` (find where `seek:` policies are handled; the runtime exports `game_set_hands`, `game_status`, `world_call` as `tools/minigolf-verify.mjs` uses them through `window.__rt`): per shot read the thing's and the current target's positions from `game_status`, fetch `ground.profile`, plan, play the swing frames through `game_set_hands` one per animation frame, wait for the thing to rest (as `restBall` does) or the game to advance, update the scale with `nextScale`, repeat up to 14 shots per target; the answer reports status, strokes per target, shots taken, the last shot's plan, and whether the game was won. Keep the existing headless policies untouched. Document the policy in the `playtest` description in one sentence and in the `game` guide topic with an example (`policy: "aim:ball:cup1,cup2,cup3"`).
