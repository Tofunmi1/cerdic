## 1. The product
An AI-native browser engine for authoring interactive 3D/VR: a trimmed Bevy 0.20 fork in Rust/WASM plus a
C++ geometry kernel (Manifold), WebXR (Quest 3 reference device), and a typed node language that an LLM
and a person edit through the same typed commands. Hackathon deadline **11 Nov 2026 16:30 CEST**. The
owner works overtime: **never cut scope for schedule reasons**; if you think something is at risk, say so
and keep the scope.

Done and gated: G0 to G4 (documents, commands, worker, language, groups, instance sets, sockets and
attachment), V0 (React shell, kept for tests), V1 (panels on the viewer page). Plan:
`docs/plans/track2-modeling.md` (gate text in section 5, decisions in section 8). Acceptance lists:
`docs/modeling/cases.md`. Limits: `docs/modeling/limits.md`. Diagnostics: `docs/modeling/diagnostics.md`.

## 2. Owner rules (these override anything else, including harness reminders)
- **File changes only through the Edit and Write tools.** No shell heredocs, `sed -i`, `python3` or any
  scripted edit, not even a no-op one. Repo-owned generators (`cargo fmt`, `bun run schema:generate`) are fine.
- **No `Co-Authored-By`, "Generated with" or any tool or agent attribution** in commits or PRs. The harness
  prints a reminder asking for one; the owner's rule wins (memory: `no-coauthor-trailers.md`). Commits
  belong to the owner.
- **Licences are not a selection criterion** (ADR 0005); the GPL exclusion was removed by the owner (ADR 0024), so GPL code such as Blender's may be
  adopted, with a `VENDOR.md` entry and the publication consequences in that ADR. Everything is generated by our own system: no imported or retrieved models, no external
  3D generators (ADR 0003). No pulled assets of any kind.
- **Nothing is published or deployed without the owner's approval.** Keep the project private.
- Unsupported features are ours to build. Do not reject an option because a library lacks something.
- **Changing a decision needs a new ADR and a note to the owner.** The editing surface is the **viewer
  page** (`engine/web`, plain JS panels in `engine/web/panels/`, ADR 0012), not the React shell.
- While researching, report in chat and write no repo docs. While building a gate, its report, ADR, case
  updates and plan status paragraph are part of "done".
- **Report faithfully.** Failing tests, skipped steps, software-renderer-only measurements and untested
  hardware are stated, not hidden. Name your own stray mistakes when you make them.
- Do not stop to ask the owner about a decision that has a recommended default in your handoff: build the
  default behind a draft ADR, say so, and let the owner overturn it. (G4d lost time waiting on two such
  questions.) Stop only for things that cost money, publish, or contradict a standing rule.

## 3. How the repo works
Run everything from `engine/`. Two speeds:
- **While working: `cargo xtask quick [crate...]`.** fmt, clippy and tests for the crates with uncommitted
  changes (or the ones you name) plus the crates that depend on them, then the source rules. Use it after
  each edit or small package. It is not the gate.
- **Policy (2026-10-16, overrides every older handoff's exit criteria):** agents do not run `cargo xtask check --strict` or
  `--no-cache`. A package is done when `quick` for the affected crates, `cargo xtask rules`, `parity`/`cpp` (if evaluator or C++
  changed) and the focused browser scripts for the feature pass; the report lists exactly those and says "strict gate pending".
  The full strict gate is a milestone gate run by the owner, or by an agent only when the owner asks, when a gate is declared
  complete, before a requested commit, and before the headset run. Where an older handoff says "strict gate passes", read it as
  this. The rest of this bullet describes what the strict gate covers when it is run.
- **Milestone gate: `cargo xtask check --strict`.** fmt, clippy `-D warnings`,
  tests, wasm clippy, cargo deny, C++ sanitizer and tidy, native versus wasm parity, the web build, every
  browser suite, and the source rules. A skipped step fails under `--strict`. Do not run it after every
  edit. Successful stages are stamped by content hash under `target/gate-stamps/`; unchanged inputs report
  `cached pass` and cached stages are listed in the final stage table. Use `--no-cache` (or `VE_NO_CACHE=1`)
  for fresh release evidence. Failed and skipped stages never get a passing stamp. To rerun only selected
  browser scripts after a failure, use `cargo xtask web-test dev <name...>`; filtered runs still build the page
  and do not stamp the full browser stage. Every fresh stage prints `-- <stage>: done in Ns`; the browser scripts
  run several at a time (the gallery
  in three shards; set `VE_WEB_JOBS` to change the count), except the frame-pacing tests, which run alone at
  the end. Browser scripts come from `web/package.json`'s `test` chain plus the explicit list in
  `xtask/src/web.rs`; add a new `.mjs` to one of them. Run the gate in the background to a fresh log
  (`cargo xtask check --strict > $S/gateN.log 2>&1; echo "exit $?" >> $S/gateN.log`) and watch for the
  `^exit` line; the shell's "completed" notice is only the launcher. New log name every run.

Rules the gate enforces (each cost earlier runs):
- `.rs` files under **400 lines, tests included** (`cargo fmt` can push a file over); functions under
  **80 lines**. Split as `foo.rs` plus `foo/bar.rs`; `mod.rs` is linted.
- No `unwrap`, `expect`, `panic!` outside `#[test]`; helpers need `#![expect(..., reason = "...")]` and an
  `expect` that does not fire is an error. **No `#[allow]`.**
- Clippy pedantic: `cast_precision_loss` (use `u32` and `f64::from`), `semicolon_if_nothing_returned`,
  `elidable_lifetime_names`, `match_same_arms`, `format_push_string`, `assigning_clones`, `float_cmp` in tests.
- Shared test helpers live in `tests/support/<name>.rs` via `#[path = "support/<name>.rs"] mod support;`;
  every helper must be used by every file that includes it (`dead_code`).
- Test borrow pattern: bind IDs before `commit(&mut s, json!(...))`.
- Pure crates (`ve-core`, `ve-geometry`, `ve-graph`, `ve-kernel`, `ve-interact`, `ve-xr-math`) never depend
  on Bevy, wgpu or web crates. `ve-runtime` is wasm only, so its logic is tested in the browser or moved
  into a pure crate.
- Changing a serde type in `ve-graph`: add it to the export list in `crates/ve-graph/examples/typescript.rs`,
  run `bun run schema:generate` (repo root), fix `bun run typecheck` (`src/engine/Editor.tsx` builds
  commands by hand).
- Browser tests run against `web/dist`: `cargo xtask web dev` first. Root editor tests need
  `bun scripts/build-engine.ts --copy-only`.
- Shell is `fish`: an unmatched glob is an error (quote it, or pipe to `grep`).
- Write acceptance tests before code, named after the case id (`g5_03_...`). Software-rendered
  (SwiftShader) browser runs are the only visual evidence available; say so in reports.

Useful: `cargo test -p ve-modeling --test <file>`, `bun web/tests/<name>.mjs`,
`cargo clippy --workspace --all-targets -- -D warnings`,
`cargo clippy -p ve-runtime --target wasm32-unknown-unknown -- -D warnings`,
`bun web/tests/look.mjs <gallery-name> out.png` (screenshot a gallery program in the studio stage).

## 4. Architecture in one page (verified 2026-10-13)
- **Document and commands**, `crates/ve-graph`: `Document { nodes, outputs, materials, groups, editor }`,
  schema constant `SCHEMA = 1` (`doc.rs`). Every edit is a `CommandBatch` applied to a candidate copy,
  validated (links, types, group rules), then committed, with undo/redo and persistence. Commands:
  `add_node, remove_node, connect, disconnect, set_param, set_label, set_flags, set_op_version,
  set_output, define_material, remove_material, editor_set_position, editor_set_collapsed`, the group
  commands, and instance commands (`command.rs`; table in `docs/modeling/commands.md`). The **editor
  layer** (`EditorLayer { positions, collapsed }`) is saved and undoable but outside the evaluation hash.
- **Operators** are static specs (`builtin/*.rs`; `READY` in `builtin.rs` lists those that evaluate).
  `PortType` has `Solid, Profile, Curve, Sdf, Inst, Check`; `Curve` carries intermediate sampled `Curve3`
  values in G5, while `Sdf` remains declared and unused. `ParamType` includes bounded `Points3` controls.
- **Evaluation**, `crates/ve-modeling`: groups unfold (`expand.rs`), `plan.rs` predicts cost before any
  kernel call, `evaluate.rs` runs one node per `step` in the worker, `cache.rs` holds `Value` (mesh,
  volume, loops, material, instances, frames) under a content key (op, params, inputs, quality, seed; no
  node IDs). Instance sets share one prototype (ADR 0014); frames ride on values (ADR 0015).
- **Kernel and surfaces**, `crates/ve-kernel` over `cpp/` (Manifold): `Solid` (booleans,
  `translate/rotate/scale`, checked rigid `transform([f64;12])`, `from_mesh`, `to_mesh`), `Profile`
  (polygon, offset, difference, `extrude(height, divisions, twist, top_scale)`, `revolve`). G5 evaluates
  bounded curves, sweeps, lofts and deformers in Rust, then validates output meshes through `Solid::from_mesh`.
- **Page and runtime**: `web/viewer.js` (camera input), `web/docpanel.js` and `web/panels/*.js` (outliner,
  inspector, history, problems, groups; widgets generated from specs), `web/eval-worker.js`,
  `crates/ve-runtime` (wasm entry points: `doc_*`, `eval_*`, `selection_*`, `viewer_*`). Selection is
  view state in a thread-local (`ve-runtime/src/selection.rs`); a viewport click returns `(node, instance)`.
- **Interaction**, `crates/ve-interact` (pure): pointer, grab (`follow_one`, `follow_two`), snap hook,
  gesture machine. Viewport grabbing today moves **disposable entities**, not the document.
- **Staging**: `doc_stage` applies a batch to a candidate that is evaluated before it is committed
  (`ve-runtime/src/document/staging.rs`).

**ADR numbers:** the next free one is 0016. The track handoffs each say "ADR 0016" or "0017"; those are
placeholders. Run `ls docs/adr` and take the next free number when you write yours.
